# Deep-dive: сверка с реестром ЦБ при сборке и бейдж «В реестре Банка России»

Идея `cbr-registry-gate-badge`. Проверено 19.10.2026: curl к cbr.ru, разбор `list_MFO.xlsx` средствами stdlib, чтение `web/` в `/Users/deniskononov/rencredit-pilot-wt`. Код не менял.

**Вердикт: do_now, 7/10, MVP за 1–1,5 дня.** Новых посетителей фича не приведёт, но баг в данных она находит уже сейчас (см. §1.4: Уралсиб). Плюс YMYL-обещание «все организации из реестра ЦБ» становится проверяемым. Карточка идеи переоценивает две вещи. Impact ближе к medium, чем к high. Подпись «проверено <дата сборки>» вводит в заблуждение: дата должна быть датой снимка ЦБ (§4).

## 1. Реальность: источники живы?

### 1.1 Реестр МФО: `list_MFO.xlsx`

- `https://www.cbr.ru/vfs/finmarkets/files/supervision/list_MFO.xlsx` отдаёт 200, 1 440 693 байт, `last-modified: Mon, 19 Oct 2026 03:43:22 GMT`. ЦБ обновляет файл ежедневно, ключа нет, лимитов не видно. Это открытые данные регулятора, перепубликация фактов (номер, вид, дата) допустима.
- Внутри обычный OOXML: `sharedStrings.xml` (4,6 МБ) и 4 листа. Порядок листов в `workbook.xml` и их строки:

| Лист | Строк | Шапка на строке | Колонки |
|---|---|---|---|
| Действующие | 812 (807 записей) | **5** | B рег. №, C дата внесения, D вид, E ОГРН, F ИНН, G/H наименование, J сайты, K тел., L e-mail |
| Действующие МФК | 28 (25) | 3 | то же |
| Действующие МКК | 785 (782) | 3 | то же |
| Исключенные | 9 507 (9 504) | 3 | B рег. №, C дата внесения, **D дата исключения**, E вид, F ОГРН, G ИНН… |

- Во второй строке каждого листа есть дата среза: «…по состоянию на 19.10.2026 (00:00 МСК)». Её и нужно выводить в бейдже.
- Подвох для парсера: у листа «Действующие» шапка на 5-й строке, у остальных на 3-й. Шапку надо искать по тексту «Регистрационный номер записи», а не по индексу строки. Среди действующих 25 МФК и 782 МКК. Пересечений номеров между «Действующими» и «Исключёнными» нет.

### 1.2 Сверка 22 МФО-офферов (19.10.2026)

Все 22 `cbrLicense` нашлись на листе «Действующие», ОГРН совпадает с `offer-sources/<slug>.json → registry.ogrn` у 22 из 22. Ручной маппинг ИНН не нужен, утверждение из карточки идеи подтверждается. Вид: 4 МФК (bystrodengi, dobrozaim, kotozaim, kviku), остальные МКК. Даты внесения: от 08.07.2011 (Быстроденьги, Саммит) до 17.04.2025 (Лайк Мани, БАЗИС).

Есть и побочная находка: в колонке J («Адреса официальных сайтов») нет 4 доменов из `officialUrl`.

| slug | officialUrl | сайты в реестре |
|---|---|---|
| dengi-na-dom | denginadom.ru | beregny.ru |
| kotozaim | kotozaim.ru | www.dobrozaim.ru |
| nebus | nebusfinance.ru | basisfin.ru |
| vash-kredit | vashcredite.ru | www.srochnodengi.ru |

`финтерра.рф` совпал после IDN-нормализации: `xn--80ajiuqaln.xn--p1ai`. Без `url.domainToUnicode` будет ложная тревога. Это может быть законный бренд-сайт того же юрлица, поэтому в коде только `warn`, не ошибка. Но ровно такую вещь пользователь проверяет руками («сайт есть в реестре?»), так что редакции стоит знать о ней заранее. В чёрном списке ЦБ этих 4 доменов нет (§1.5).

### 1.3 Банки: `CreditOrgInfo.asmx`

- SOAP `https://www.cbr.ru/CreditInfoWebServ/CreditOrgInfo.asmx` жив, WSDL отдаётся, ключа нет. Нужны операции `EnumBIC` (один вызов, 150 КБ, 638 КО, поля `RN`, `intCode`, `NM`), `CreditInfoByIntCodeXML` (`OrgStatus`, `MainRegNumber` = ОГРН, лицензии `LIC/LDate`) и `LastUpdate`.
- 8 банковских офферов (akbars-115, alfa ×2, halva, otp-120, ozon, tbank ×4, uralsib-120) сверяются по 7 номерам: 2590, 1326, 963, 2766, 3542, 2673 и «30».

### 1.4 Реальный баг, который сверка находит сразу: Уралсиб

- `content/offers/uralsib-120.json`: `cbrLicense: "30"`, в `offer-sources` то же «30». На живом сайте `/karty/uralsib-120/` выводится «Номер в реестре ЦБ РФ: 30».
- Реестр ЦБ (`foinfo/?ogrn=1020280000190`, `EnumBIC`, `CreditInfoByIntCodeXML`) говорит другое: **регистрационный номер ПАО «БАНК УРАЛСИБ» — 2275**, БИК 044525787. «30» — номер генеральной лицензии, которую банк указывает в своей рекламе (получена при присоединении), а в реестре КО это другое поле.
- Наивный поиск по номеру даёт ложь: `RegNumToIntCode(30)` возвращает **ОАО АКБ «АВТОБАНК-НИКОЙЛ», статус «ликвидирована»**. Подтверждено риском из идеи: короткие банковские номера нельзя искать ни подстрокой, ни через `RegNumToIntCode`. Сверять нужно по ОГРН. Номер 30 в `EnumBIC` отсутствует, 2275 есть.
- Текущий `check-content.mjs` этого не ловит: он сравнивает `cbrLicense` с `registry.regNumber`, а оба поля набраны руками из одного источника.
- Исправление данных: `cbrLicense: "2275"` в оффере и источнике. Если нужна лицензия, отдельная строка «Генеральная лицензия № 30», но только со ссылкой на первоисточник.

### 1.5 Чёрный список (warning-list) — для полной версии

`https://www.cbr.ru/ref/blacklist/BlackList.xml` (301 → `/Queries/FileSource/123124/BlackList.xml`) весит **13,8 МБ** и отдаётся медленно: за 54 с пришло около 400 КБ. Записи `<RC>` с полями `Site`, `INN`, `Sign`, `DT`. Для MVP он не нужен: наши кредиторы и так в реестре. Пригодится как сверка доменов в полной версии, с таймаутом в несколько минут и кешем.

### 1.6 Доступность cbr.ru из CI (не проверено)

Деплой задуман через GitHub Actions (`.github/workflows/deploy-rencredit.yml`, пока только `workflow_dispatch`). С раннеров GitHub в США доступ к cbr.ru я не проверял: прямых данных о гео-блоке не нашёл ([поиск](https://meduza.io/en/news/2026/05/08/github-access-deteriorates-in-russia-as-internet-regulator-denies-blocking) находит только обратную проблему, деградацию доступа к GitHub из РФ). Поэтому сеть и сборку надо развести: `sync-cbr.mjs` пишет закоммиченный снимок, сборка читает только файл. Если сеть недоступна, сборка остаётся детерминированной на старом снимке, а контроль свежести ловит устаревание (§4).

## 2. Код: куда встраивается

Что есть сейчас:

- У всех 33 офферов есть `cbrLicense` и `legalName` (`packages/core/src/types.ts:61`). В `src/data/offer-sources/<slug>.json` лежит `registry {source, regNumber, ogrn, inn, url, status:"active", name}`, набранный руками 13.10.2026. `registry.url` уже ведёт на `cbr.ru/finorg/foinfo/?ogrn=…` (страница отдаёт 200 и показывает «Статус УФР: Действует» и запись «Микрофинансовая деятельность <рег.№> – <дата>»).
- Вывод: `pages/[dir]/[slug].astro:53-56`, блок «Юридические данные», строка `['Номер в реестре ЦБ РФ', o.cbrLicense]` статичным текстом без ссылки и даты. `OfferCard.astro` номер не показывает.
- В `pros` рукописные фразы вроде «МФК в государственном реестре ЦБ с 2011 года» (bystrodengi): это та же дата из колонки C, её можно генерировать.
- Обещания без проверки: `Calculator.astro:45` («Все организации — из реестра ЦБ РФ»), `Footer.astro:16`, `lib/ui/site.ts:35`.
- `web/scripts/check-content.mjs` проверяет `checkedAt ≤ 30 дней`, наличие `registry.regNumber/url` и `cbrLicense === registry.regNumber`, только у `verified=true`. **Скрипт не подключён ни к CI, ни к `scripts/check.mjs`, ни к `prebuild`**: его запускают руками (README, шаг 4). Значит, «сборка падает» сейчас ничем не обеспечено. Отдельно: срок `checkedAt=2026-10-13` + 30 дней истекает **12.11.2026** у всех `verified`-офферов. Если подключить скрипт к CI, с этой даты сборка начнёт падать.
- `sync-cbr.mjs` и `cbr_registry.json` из карточки идеи **не существуют** ни в rencredit-pilot-wt, ни в mosseo-site-pipeline. Готового xlsx-парсера в `web/` тоже нет.
- Сборка: Astro 7 static, офферы через `getCollection('offers')` в `lib/offers.ts:getOffers()`. Хостинг — статика на Beget, заливка через lftp mirror.

Совместимость: всё работает на этапе сборки. **Клиентского JS 0 байт**: бейдж — разметка внутри уже существующих SSR-компонентов. Снимок реестра (около 30 записей, 6–8 КБ) импортируется в `.astro` и в бандл не попадает. PHP не нужен.

Парсер без новых зависимостей: `unzip -p list_MFO.xlsx xl/workbook.xml xl/_rels/workbook.xml.rels xl/sharedStrings.xml xl/worksheets/sheetN.xml` через `execFileSync` (unzip есть на macOS и ubuntu-latest) плюс регулярки по `<si>/<t>` и `<c r=… t="s"><v>`. В прототипе на Python stdlib (`zipfile` + `ElementTree`) это 30 строк, и он прошёл на текущем файле. SheetJS и exceljs не нужны.

## 3. Ценность

### Пользователь и поведенческие факторы

Вместо голой цифры «2110573000002» пользователь видит: «В реестре Банка России · МФК · с 08.07.2011 · данные ЦБ на 19.10.2026 ↗». Ссылка ведёт на карточку организации на cbr.ru: проверка занимает один клик, а не «скопируйте номер и найдите сам». На обзоре это снимает возражение «а не мошенники ли» прямо перед CTA. Ожидаемый эффект — немного выше CTR на «Получить деньги» и меньше возвратов в выдачу на брендовых страницах. Измерить пока нечем (цели Метрики на CTA — отдельная задача). Оценка — гипотеза.

### SEO

- Прямого трафика бейдж не даёт. Косвенно он работает на E-E-A-T/YMYL: проверяемая ссылка на регулятора, видимая дата актуальности и факт вместо маркетинговой фразы. Это прямо закрывает пункт 15 SEO-аудита (`06-eeat-legal-trademark.md`: «ежемесячную сверку с реестром стоит автоматизировать»). Сам аудит я не дублирую.
- Брендовые long-tail запросы вида «<бренд> лицензия цб», «<бренд> есть в реестре цб», «<бренд> легальная мфо», «<юрлицо> мкк отзывы» (частоты не снимал, Wordstat недоступен). Сейчас на них отвечает строка с номером. Дешёвое усиление для полной версии — пункт FAQ «Есть ли <name> в реестре ЦБ?» с ответом из снимка: вид, дата внесения, дата среза.
- Свежесть: снимок ЦБ обновляется ежедневно, это честный повод пересобирать сайт раз в неделю и показывать дату. Но cron деплоя закомментирован, так что выгода появится только после его включения.
- Ссылкоёмкость низкая: на бейдж ссылаться не будут. Отдельная страница «Проверка МФО по реестру ЦБ» по полному списку из 807 записей — это другая идея (`mfo-trust-proverka`), к MVP не относится.

### Монетизация

Защита, а не рост. Реклама организации, исключённой из реестра, — нарушение ч. 13 ст. 28 38-ФЗ (на эту норму в коде уже ссылаются). Кроме того, это риск блокировки сайта или расторжения со стороны CPA-сети. Исключения из реестра случаются регулярно: 9 504 записи за всё время, пачками. Для наших 22 крупных МФО вероятность мала, но цена ошибки высокая, а проверка почти бесплатна.

### Юридические риски самой фичи

- **38-ФЗ.** Бейдж — факт о рекламодателе. Нельзя формулировать «одобрено ЦБ» или «рекомендовано Банком России» и ставить эмблему ЦБ: это вводит в заблуждение и использует символику регулятора. Формулировка: «В реестре Банка России» + вид + дата + источник.
- **Достоверность даты.** «Проверено <дата сборки>» при старом снимке — недостоверная информация. Выводить дату среза из xlsx («по состоянию на 19.10.2026»), а не `Date.now()` в момент сборки.
- **152-ФЗ** не затрагивается: публичные сведения о юрлицах, данные пользователей не собираются.
- **Финсоветы**: бейдж не рекомендует, а констатирует статус. Рядом остаётся существующий дисклеймер «окончательные условия определяет кредитор».

## 4. MVP (1–1,5 дня)

1. **`web/scripts/sync-cbr.mjs` (новый, около 90 строк, без зависимостей).**
   - МФО: скачать `list_MFO.xlsx` → `unzip -p`. Листы найти по имени через `workbook.xml`, шапку — по тексту «Регистрационный номер записи», колонки — по заголовкам.
   - Предохранители от смены формата: на листе «Действующие» ≥ 500 записей, дата «по состоянию на» распарсилась и отстаёт не больше чем на 3 дня, у каждой записи 13–15 цифр в номере и 13 в ОГРН. Иначе `exit 1` без перезаписи снимка, чтобы не получить ложное «не в реестре».
   - Банки: `EnumBIC` → `intCode` по точному `RN === Number(cbrLicense)`, затем `CreditInfoByIntCodeXML` для 7 банков. Требовать `MainRegNumber === registry.ogrn` и `OrgStatus === 'норм.'`.
   - Записать `apps/rencredit/src/data/cbr-registry.json`: `{ asOf, fetchedAt, counts, byLicense: { "<рег.№>": { kind: "МФК|МКК|банк", since, ogrn, name, status: "active|excluded|missing", excludedAt?, sites? } } }` — только номера наших офферов и сервисов.
2. **`check-content.mjs` (около 20 строк).** Для каждого оффера с `cbrLicense`:
   - статус в снимке ≠ `active` → `err`, с датой исключения из листа «Исключенные»;
   - ОГРН снимка ≠ `registry.ogrn` → `err`;
   - `asOf` старше 14 дней → `err` («запустите sync-cbr»);
   - хост `officialUrl` (через `domainToUnicode`) не входит в `sites` → `warn`.

   Теперь это делается для всех офферов, а не только для `verified`.
3. **`lib/offers.ts` (около 8 строк).** `registryOf(o)` из импортированного JSON. В `getOffers()` отбрасывать офферы со статусом ≠ `active` с `console.warn`. Это вторая линия защиты: даже если check-content не запускали, реклама исключённой МФО не соберётся, а деплой новостей не блокируется.
4. **Бейдж.** `components/RegistryBadge.astro` (новый, около 25 строк, два места использования):
   - на обзоре (`[dir]/[slug].astro`) — заменить строку «Номер в реестре ЦБ РФ» на «В реестре Банка России: МКК, рег. № …, с 07.03.2018 · данные ЦБ на 19.10.2026» со ссылкой `registry.url` (`rel="noopener"`, без nofollow — это первоисточник);
   - в `OfferCard.astro` — компактный текст «В реестре ЦБ · МКК» без внешней ссылки (33 карточки × внешняя ссылка в каталоге — лишнее), полная строка в `title`;
   - в JSON-LD обзора добавить `provider: {Organization, name: legalName, identifier: ОГРН, sameAs: registry.url}`. Сейчас `ld` в `[slug].astro` собирается без `provider`, хотя в `core/schema.ts` он есть.
5. **Данные.** Уралсиб: `cbrLicense` и `registry.regNumber` `30 → 2275` (`content/offers/uralsib-120.json`, `data/offer-sources/uralsib-120.json`).
6. **CI.** В `deploy-rencredit.yml` перед Build добавить шаги `node web/scripts/sync-cbr.mjs || true` (при недоступности cbr.ru остаётся закоммиченный снимок) и `node web/scripts/check-content.mjs`. Учесть, что с 12.11.2026 упадёт проверка `checkedAt` (см. §2): решить заранее — пересверка или понижение до `warn`.

Проверка (один runnable check): `node web/scripts/check-content.mjs` с подменённым снимком, где у одного оффера `status: "excluded"`, должен выйти с кодом 1. Без подмены — OK. После сборки `grep "по состоянию" dist/mfo/bystrodengi/index.html`.

## 5. Полная версия (+2–3 дня, после MVP)

- Еженедельная пересборка: включить `schedule` в workflow, когда пройдёт первый ручной деплой. Без неё дата в бейдже стареет; check-content ловит это после 14 дней.
- Уведомление о смене статуса: diff снимков (`active → excluded`, смена юрлица или сайта) в Telegram или почту владельцу. Канал — тот же, что для B5.5 / mail.php.
- Сверка доменов по `BlackList.xml` (13,8 МБ, медленно, с кешем): `officialUrl` и конечный домен лендинга не в чёрном списке.
- Генерируемые из снимка `pros` («МКК в реестре ЦБ с 2018 года») вместо рукописных и FAQ «Есть ли X в реестре ЦБ?» на обзорах.
- Сервисы (страхование, РКО, вклады): страховщики — реестр субъектов страхового дела, банки — тот же `CreditOrgInfo`. `check-content` уже сравнивает `cbrLicense` у services, но только с ручным `registry`.
- Переиспользование в сети: тот же `sync-cbr.mjs` подходит finhelp-ru (там идея №11 с 157 страницами `/zaim/*`). Вынести в `packages/core` можно, когда появится второй потребитель.

## 6. Риски и ограничения

| Риск | Мера |
|---|---|
| Сменится структура xlsx (листы, шапка, колонки) | Поиск листа, шапки и колонок по тексту, минимум 500 строк, дата среза; при сбое — exit 1 без перезаписи снимка |
| Короткие банковские номера (30, 963) | Только точное равенство `RN` + сверка ОГРН; `RegNumToIntCode` не использовать (для «30» вернёт ликвидированный банк) |
| cbr.ru недоступен из CI | Закоммиченный снимок, `sync || true`, контроль свежести 14 дней |
| Без пересборки дата устаревает | В бейдже дата среза ЦБ, а не «проверено сегодня»; check-content требует свежий снимок |
| Ложная тревога по доменам (IDN, бренд-сайты одного юрлица) | `domainToUnicode`; только `warn` |
| check-content сейчас не в CI | Подключить; плюс фильтр в `getOffers()` как вторая линия защиты |

# Site Architecture Notes

## Goal

Build the future site so content, templates, SEO metadata, structured data,
analytics, forms, and deployment are separate layers. This keeps the site easy
to redesign without losing SEO or re-parsing content.

## Core principle

Content data must not be tied to one visual design.

Use this separation:

- `site_pipeline/output/pages/*.json` - raw extracted content.
- `site_pipeline/output/build_manifest.json` - buildable route list.
- `site_pipeline/output/redirects.json` - redirects.
- Site generator templates - visual layouts and page composition.
- SEO/schema helpers - reusable metadata and structured data generation.
- Site config - analytics IDs, company contacts, deploy settings, feature flags.

When a design changes, update templates/components. Avoid editing generated page
JSON unless the source content itself is wrong.

## Recommended generator shape

Astro is the preferred first choice for this project because the dataset is
mostly static, content-heavy, and SEO-sensitive.

Suggested structure:

```text
site/
  astro.config.mjs
  src/
    data/
      loadPages.ts
      siteConfig.ts
    layouts/
      BaseLayout.astro
      ArticleLayout.astro
      ArchiveLayout.astro
      ServiceLayout.astro
      PortfolioLayout.astro
      ContactLayout.astro
      HomeLayout.astro
    components/
      SeoHead.astro
      JsonLd.astro
      Header.astro
      Footer.astro
      Breadcrumbs.astro
      ContactForm.astro
      Analytics.astro
      PromoSlot.astro
      AffiliateLink.astro
    lib/
      routing.ts
      seo.ts
      schema.ts
      links.ts
      affiliate.ts
    pages/
      [...slug].astro
      404.astro
```

## Page type mapping

Determine page type from section/path and optionally from page metadata:

- `/` -> `home`
- `/faq/` and `/faq/...` -> `faq` / `article`
- `/portfolio/` -> `portfolio_archive`
- `/portfolio/...` -> `portfolio_case`
- `/seo-uslugi/...` -> `service`
- `/konsultacii-.../...` -> `service_or_article`
- `/vse-o-seo-prodvizhenii/...` -> `blog_archive` or `article`
- `/seo-wikipedia/` -> `dictionary_archive`
- `/seo-wikipedia/...` -> `dictionary_article`
- `/kontakty/` -> `contact`
- `/o-kompanii/...` -> `company`
- fallback -> `content_page`

Keep this mapping in code/config so it can evolve without changing extracted
content.

## SEO metadata

Every generated page should derive SEO fields in this order:

1. CSV seed metadata from page JSON.
2. HTML metadata from extracted page.
3. WordPress title.
4. Generated fallback from H1/title/path.

Per-page output:

- `<title>`
- `<meta name="description">`
- canonical URL
- Open Graph title/description/url/type
- Twitter card tags if needed
- one H1 where the template controls the heading
- breadcrumbs where appropriate

Do not blindly inject an extra H1 if `content_html` already contains the visible
H1. Normalize this per template.

## Structured data / microdata

Use JSON-LD generated by a shared `schema.ts` helper. Do not hardcode schema
inside each template.

Base schemas:

- `Organization` for the company/site identity.
- `WebSite` for the root site.
- `BreadcrumbList` for pages with hierarchy.

Page-specific schemas:

- Home page:
  - `Organization`
  - `WebSite`
  - optional `WebPage`

- Contacts page:
  - `ContactPage`
  - `Organization`
  - contact points if reliable phone/email/address data is available

- Blog/articles:
  - `Article` or `BlogPosting`
  - `BreadcrumbList`
  - include headline, description, mainEntityOfPage, datePublished/dateModified
    when available from WordPress metadata

- SEO Wikipedia/dictionary articles:
  - `Article` or `DefinedTerm` / `DefinedTermSet` if the content is truly a
    glossary term
  - `BreadcrumbList`

- FAQ pages:
  - `FAQPage` only when the page has real question/answer pairs
  - otherwise use `Article`

- Service pages:
  - `Service`
  - `WebPage`
  - `BreadcrumbList`
  - optional `Offer` only when pricing is explicit and reliable

- Portfolio/case pages:
  - `CreativeWork`, `Article`, or `CaseStudy`-like representation using
    `CreativeWork` because schema.org does not have a universally supported
    `CaseStudy` type
  - `BreadcrumbList`

- Archive/category pages:
  - `CollectionPage`
  - `ItemList` for listed posts/cards if list items are cleanly available

Important rules:

- Only emit schema fields that are known and reliable.
- Do not invent ratings, reviews, prices, addresses, or publication dates.
- Validate JSON-LD after templates are implemented.
- Keep schema generation deterministic from page data and site config.

## Design flexibility

Design changes should happen in these layers:

- Layouts define macro page structure.
- Components define reusable UI.
- CSS/theme tokens define visual design.
- Page type mapping decides which layout a route uses.
- Content JSON remains stable.

Avoid putting page-type-specific parsing logic inside visual components. Parsing
and classification should happen before rendering or in `lib/routing.ts`.

Suggested design tokens:

```text
colors
typography
spacing
container widths
header/footer variants
button styles
content typography
card/list styles
form controls
```

This lets us redesign article pages, service pages, and portfolio pages without
changing content extraction.

## Forms and analytics

Keep analytics and forms isolated:

- `Analytics.astro` reads IDs from config/env.
- `ContactForm.astro` is reusable and only appears on chosen templates.
- Form backend settings are config-driven.
- Anti-spam is part of form handling, not a global blocker on content pages.

## Affiliate / partner links and traffic arbitration

The site may need partner links, sponsored links, traffic-arbitrage placements,
and promotional text blocks inside articles, contacts, service pages, or other
high-value pages.

Do not hardcode these links directly into templates or page HTML. Use a
separate configuration/data layer so links and sponsors can be changed quickly
without re-parsing content or editing hundreds of pages.

Suggested structure:

```text
site/
  src/
    data/
      affiliateLinks.json
      promoSlots.json
```

Suggested `affiliateLinks.json` fields:

```json
{
  "id": "sape-2026-market-report",
  "label": "Sape research 2026",
  "href": "https://example.com/?ref=...",
  "rel": "sponsored nofollow",
  "utm": {
    "source": "mosseo",
    "medium": "article",
    "campaign": "sape-2026"
  },
  "enabled": true
}
```

Suggested `promoSlots.json` fields:

```json
{
  "id": "article-footer-sponsor",
  "enabled": true,
  "placement": "article_footer",
  "sections": ["vse-o-seo-prodvizhenii", "seo-wikipedia"],
  "paths": [],
  "html": "<p>Спонсором этого поста выступили ...</p>",
  "link_ids": ["sape-2026-market-report"]
}
```

Placement rules:

- Slots should be addressable by page type, section, path, tag, or exact page ID.
- Keep promotional copy editable from one config file.
- Keep link targets editable from one config file.
- Allow disabling a campaign globally with `enabled: false`.
- Add UTM tags in a helper, not manually inside every link.
- For paid/sponsored/affiliate links, default to `rel="sponsored nofollow"`.
- For internal partner pages or owned properties, choose rel attributes
  intentionally.
- Keep a central audit list of all outbound monetization links.

Example use case to preserve:

- An article may include commentary about the Sape 2026 link-market research.
- It may include sections like PBN, portals/media, IKS filtering, rental links,
  and profitable niches.
- A sponsor line such as "Спонсором этого поста..." should be configurable as a
  promo slot, not hardcoded into the article body.

SEO and compliance notes:

- Sponsored/affiliate links should be marked clearly where required.
- Avoid injecting hidden links.
- Avoid cloaking different links for users and crawlers.
- Keep partner links easy to replace or remove before launch.
- Track clicks only in a privacy-conscious way and avoid leaking sensitive form
  data into analytics URLs.

## Build outputs

Future generator should produce:

- static HTML for `build_manifest.json`
- `sitemap.xml`
- `robots.txt`
- redirects config compatible with Beget hosting setup
- optional static assets copied/proxied if needed

## Pre-launch validation

Before deployment:

- Run page count check: generated pages = buildable pages.
- Validate redirects count = `redirects.json`.
- Validate no generated page exists for `excluded_pages.json`.
- Run metadata checks for title/description/canonical/H1.
- Run JSON-LD validation on representative page types.
- Run link checks.
- Run browser smoke tests on desktop/mobile representative pages.
